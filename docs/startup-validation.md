# Startup validation

This change runs all fallible authentication and TLS prerequisites before
Hyprland discovery, capture, input, audio, session hooks or the RDP listener.
The prepared TLS acceptor and CredSSP public key are reused by the server;
files are not reopened after the preflight.

## Authentication and migration

The upstream configured-credential and PAM validators are retained. Configured
credentials still use Hybrid/CredSSP and authenticated preemption. PAM still uses
TLS, the desktop user's PAM validator and the existing queue policy. A typo or
incomplete credential configuration must never implicitly select anonymous access.

* `configured` remains the default and requires a nonempty username and password.
  A missing or empty password file is an error, with the existing CLI precedence.
* Intentional anonymous access remains available through `auth_mode = "none"`
  or `--auth-mode none`. Remove username, password, password_file and pam_service
  settings; conflicting fields are rejected even when empty.
* `pam` retains the existing service-file prerequisite and disallows configured
  credentials. Preflight does not attempt a login or PAM password verification.
* Unknown TOML keys now fail, including otherwise ignored typos. Parse errors
  report path, line, column and category without echoing source/password content.

The default-mode change is intentional: a previously anonymous configuration
must explicitly select `none`. It is not a claim that upstream's intentional
anonymous mode was a defect. Existing complete configured/PAM setups keep their
authentication mechanism. No subnet rules or host network configuration are added.

## TLS identity

Explicit cert/key paths must be supplied together. Default paths remain
`~/.config/hypr-rdp/cert.pem` and `key.pem`. The loader opens each file once,
checks the opened descriptor is regular, limits each PEM file to 1 MiB, and
rejects private keys with group/other permissions. Symlinks to regular files
remain supported; validation applies to the opened target. Nonblocking opens
prevent a FIFO from hanging the preflight.

PEM/X.509 parsing, current validity of every supplied chain certificate, exactly
one private key and the leaf/key match are checked. CredSSP receives the leaf's
public-key BIT STRING, matching the pinned IronRDP helper. Rustls keeps its
default disabled key logger, including when SSLKEYLOGFILE is set. Parser errors
do not print raw key/certificate contents. The server does not determine whether
a remote client trusts the certificate or accepts its hostname; client trust
and Windows/NLA interoperability still need real-client acceptance tests.

Normal startup retains upstream's self-signed RSA generation when both default
paths are absent. It takes a nonblocking advisory provisioning lock, stages
fully written files in a private directory, and publishes with hard links that
cannot replace existing entries. Concurrent provisioning can fail with a retry
message; it does not wait indefinitely. The existing files are never rewritten.
A crash between publication of the two files leaves an incomplete identity that
fails on the next start. The two filenames are not claimed to be one atomic
transaction. Dangling symlinks count as existing entries. Restore the matching
pair explicitly after investigating a partial identity. The lock file remains
in the application config directory and carries no credentials.

Autogenerated SANs remain `localhost` and `127.0.0.1`. Use a certificate appropriate
for the actual connection name when client trust is required; this stage does not
automatically enroll trust or change host certificate stores.

## Offline check

`hypr-rdp --check-config [--config PATH]` uses the same configuration resolution,
authentication preparation and TLS loader as startup, then exits successfully.
It only reads existing identities, never generates them. Failure returns a
nonzero status before desktop access. It does not prove successful client auth,
available capture/encoders or readiness of the live desktop.

Implementation map: `src/config.rs` resolves/validates configuration,
`src/server/tls.rs` owns identity loading/provisioning, `src/server/mod.rs`
orders preparation before desktop setup, and `src/main.rs` dispatches the check.
The X.509 parser is the already locked x509-cert 0.3.0 used by IronRDP; making it
a direct dependency changes only the root dependency edge, without upgrading or
adding any of the 484 locked packages. Manifest hashes are updated explicitly.

The compatibility reference is the pinned
[IronRDP TLS helper](https://github.com/Devolutions/IronRDP/blob/3db08ba86983ce35c9d36ad33f59ceb4b607dce8/crates/ironrdp-server/src/helper.rs).
It also explains why this loader builds the acceptor directly: the helper opts
into environment-controlled key logging. Validity/public-key parsing uses the
same [x509-cert 0.3.0 API](https://github.com/RustCrypto/formats/tree/c478c6bb0db65677e85e2c0297962817eed90352/x509-cert).

## Validation and rollback

Unit tests cover configuration errors, non-disclosing diagnostics, key permissions,
key matching, validity boundaries, FIFO rejection, saved/partial identities,
busy provisioning locks and compatibility with the IronRDP public key.
`tests/startup.rs` launches the real binary on a disposable CPU CI runner with a
cleared environment, empty HOME and nonexistent Wayland runtime. It verifies
offline success even with an occupied configured port, no home/key-log writes,
and auth/TLS failures before compositor discovery. All existing feature suites,
NVENC lifecycle tests, Clippy and a frozen release build remain required.

No test in this stage uses the owner's desktop, NVIDIA GPU or production
credentials. Real PAM login, Windows/Linux/macOS connections, certificate trust,
reconnect, package install/remove and GPU qualification remain open.

This development branch is unmerged and uninstalled. Closing its draft PR changes
no running system. For a future deployment rollback, restore the previous package
and its matching config; do not delete or regenerate a working TLS identity.
Switching to the upstream default removes the explicit-anonymous requirement,
so review the restored authentication settings before starting that version.
Package rollback and full removal will be tested in the packaging stage.
